# G815 wave (ripple-on-keypress) — design

**Date:** 2026-10-13
**Status:** Approved in conversation (pending written-spec review)
**Supersedes:** Phases 2 and 3 of
`docs/superpowers/specs/2026-07-14-g815-static-controller-experiment-design.md`,
merged into one project.
**Builds on:** the Phase 1 spike, `experiments/g815_probe.py` and its findings
log `experiments/README.md`.

## Goal

When a key is pressed on the Logitech G815 (`046d:c33f`), a ring of light
expands from that key across the keyboard over a dark base color. The effect
runs as a background service from login. You switch it with the existing
`ligths` / `./lights` command. It uses our own Python code: OpenRGB, Solaar and
g810-led are references only, never runtime dependencies.

## Decisions (from the design conversation)

| Topic | Decision |
| --- | --- |
| Look | Expanding ring from the pressed key (classic ripple) |
| Ring colors | A gradient across the ring band, leading edge → tail; more than two colors |
| Base | Dark blue/purple, `#140028` |
| Presets | `red`: `#ffffff` → `#ff2a2a` → `#b0005a` → base. `blue`: `#ffffff` → `#33ccff` → `#1f4fff` → base |
| Running | systemd **user** service, started with the graphical session |
| Switching | `ligths wave red|blue|off|status` (via `./lights`), no restart needed |
| Keypress source | **X11** (python-xlib, filtered to the G815 device). No `input` group membership |
| Code location | Inside the live `logitech_lighting` package; the G560 path is untouched |
| Lock screen | Rings pause while the screen is locked (keyboard holds the base color) |
| Privacy mode | Not wanted. The visible key-position exposure is accepted |

Rejected alternatives: evdev input (needs the `input` group, which lets any
user process read all typing); a standalone script under `experiments/`
(doesn't fit the `ligths` integration).

## Architecture

New subpackage `g560ctl/src/logitech_lighting/devices/g815/`. It sits alongside
the G560 and does not implement `DeviceConfig` / `UnifiedController`, which
model 4 zones with effects run on the device over USB control transfers.

| Module | Responsibility | Pure? |
| --- | --- | --- |
| `layout.py` | Key table: name → zone id → physical center `(x, y)` in key units (1 unit = one letter-key width), US ANSI full-size + G1-G5, media keys, logo. Also X11 keycode → key name. | yes |
| `presets.py` | Base color, the two presets as gradient stops, gradient interpolation, color quantization | yes |
| `ripple.py` | Effect state: active rings, `press(key, t)`, `render(t) -> {zone: (r,g,b)}`, pause/resume | yes |
| `frame.py` | Encoder: previous frame + new frame + valid zone set → list of HID++ packets | yes |
| `hidpp.py` | HID++ 2.0 transport over hidraw: open, feature discovery, pipelined send with reply matching, BUSY handling, claim/release, zone discovery | no |
| `keys.py` | X11 XInput2 raw key-press listener for the G815 device(s) only | no |
| `daemon.py` | Main loop, control socket, state file, lock-screen watch, reconnect | no |

Data flow per frame (target 60 fps):
`keys.py` press events → `ripple.render(t)` → `frame.encode(prev, next)` →
`hidpp.send_frame(packets)` (pipelined, then frameEnd).

### CLI and service

- `logitech_lighting/cli.py` gains a `wave` subcommand with these actions:
  - `wave red` / `wave blue`: select the preset and resume rings.
  - `wave off`: pause rings and hand the keyboard back to onboard lighting.
  - `wave status`: preset, paused/active, keyboard connected, measured fps.
  - `wave daemon`: run the daemon in the foreground (used by the service).
- `wave` needs no `--device` (it is G815-only), and the G560 commands are
  unchanged. `./lights` and `~/.local/bin/ligths` already pass arguments
  through, so `ligths wave red` works with no change to either wrapper.
- The service unit is `~/.config/systemd/user/g815-wave.service`:
  - `ExecStart=<repo>/lights wave daemon`, so the group comes via `sg` as for the speakers;
  - `PartOf=` and `WantedBy=graphical-session.target`;
  - `Restart=on-failure`.
  The repo keeps the unit file and the docs explain how to install it (a
  one-time `systemctl --user enable --now`).
- Dependency: add `hidapi` (pinned `>=0.14`, using `import hidraw`, never
  `hid`) and `python-xlib` to `pyproject.toml`.

## The effect (`ripple.py`, `presets.py`, `layout.py`)

- **Geometry.** Each key has a physical center in key units, and a ring's
  distance to a key is the Euclidean distance between their centers.
- **One ring.** Born at the pressed key's center at time `t0`.
  - The radius is `r(t) = 25 units/s × (t − t0)`.
  - The band is 3 units wide behind the leading edge.
  - For a key at distance `d`, the band position is `u = (r − d) / 3`. When
    `0 ≤ u ≤ 1` the key is on the band: `u = 0` is the leading edge, `u = 1`
    the tail.
  - Its color is `gradient(u)` from the preset stops.
  - Its intensity is the ring's age envelope, which falls linearly to 0 at
    1.2 s.
  - The final color is `lerp(base, gradient(u), intensity)`.
- **Origin flash.** The pressed key shows the first gradient stop at full
  intensity for its first 80 ms.
- **Many rings.**
  - At most 8 live rings; a ninth press drops the oldest.
  - Rings expire at 1.2 s.
  - Where rings overlap, a key takes the contribution with the highest
    intensity. They are not added together.
- **Quantization.** Intensity is quantized to 16 steps before the color is
  computed. This bounds the number of distinct colors per frame, so the
  encoder can group keys.
- **Pause.** While paused, `press()` is ignored. Existing rings finish
  naturally, then the frame is all base.
- **Idle.** With no live rings, `render` returns the all-base frame. The
  encoder then emits nothing, because nothing changed.

All numeric values (speed, band width, lifetime, flash, max rings,
quantization steps, colors) are named constants in `presets.py` /
`ripple.py`, so they can be tuned after we see the effect on the keyboard.

## Talking to the keyboard (`hidpp.py`, `frame.py`)

Phase 1 facts carried forward:
- **Interface.** hidapi `hidraw` entry with usage page `0xFF43`, usage
  `0x0602` (interface 1). The kernel input driver stays attached.
- **Report format.** HID++ long reports only: `0x11`, device `0xFF`,
  20 bytes.
- **Feature indexes.** Discovered at runtime via the root feature
  getFeature, never hardcoded. Seen so far: `0x8081` per-key lighting v2,
  `0x8071` RGB effects, `0x8100` onboard profiles.
- **Zone ids.** Main block = HID usage − 3 (`0x01-0x67`), modifiers
  `0x68-0x6f`, `0x99` (backlight/indicator key), media `0x9b-0x9e`, G1-G5
  `0xb4-0xb8`, logo `0xd2`.

**Claim (take software control)**, in this order:
1. Discover the feature indexes.
2. `0x8071` SetSWControl. This stops the onboard effect engine; without
   it, the keyboard reverts to onboard colors after a few seconds
   (Solaar PR #3165).
3. `0x8100` setOnboardMode = `0x02` (host).
4. Zone discovery: `0x8081` fn 0, pages 0-2, giving a bitmap of valid
   zones. Compare it against `layout.py`. A layout zone the device does
   not report is dropped and logged once, never sent.
5. Paint the full base frame and send frameEnd.

**Release:** SetSWControl off, then setOnboardMode = `0x01`. It runs on
`wave off`, on daemon shutdown (SIGTERM/SIGINT), and on X session loss.

**Hardware verification gate (first implementation task):**
- The exact SetSWControl parameter bytes for the G815.
- Whether OpenRGB's `0x4522` (DisableKeysByUsage) handshake is needed.
- Whether host mode breaks the G-key lighting (OpenRGB has this quirk on
  the G915 TKL).

The claim sequence is fixed according to what that probe shows before
anything is built on top of it.

**Frame encoding (`frame.py`, pure).** Input: previous frame, next frame and
the valid zone set. Output: packets.
- Only zones whose color changed (plus resync zones) are sent.
- Packets are grouped to minimise the count:
  - fn 5 setRangeRgbZones for runs of ≥3 consecutive zones with one color;
  - fn 6 setRgbZonesSingleValue (≤13 zones) for scattered zones sharing a color;
  - fn 1 setIndividualRgbZones (4 zones/packet) for colors used once.
- Each frame also re-sends 2-3 zones in rotation, so a write that was
  acknowledged but dropped heals within about a second.
- A frame with no changes and no resync zones yields no packets and no
  frameEnd.
- Exact fn 1/fn 5 byte layouts are taken from Solaar `PerKeyLighting` and
  OpenRGB `LogitechHIDPP20Controller`, and pinned by unit tests.

**Sending (`hidpp.py`).**
- **sw_id.** Rotates 1-15 per request, and replies are matched on
  (feature index, function, sw_id). A stale reply cannot satisfy a later
  request, which closes the open hypothesis from the Phase 1 findings.
- **Pipelining window.** Up to N requests unacknowledged, starting at N=4,
  growing to 8 after 16 clean frames and halving after a lost reply. If a
  frame stalls for more than 60 ms, it is abandoned and the next frame does
  a full resync.
- **BUSY on frameEnd** is backpressure, not failure.
  - Sleep a learned time per zone written (smoothed, capped at 100 ms per
    frame), then retry frameEnd every 3 ms.
- **BUSY on other requests.** Retry after 30 / 60 / 90 ms, then treat it as
  an error.
- **Repeated errors** (3 frames in a row) lead to release + re-claim. A
  write/read OSError means the keyboard is gone and the daemon enters
  *waiting* (see below).
- **Frame skipping.** If rendering plus sending overruns the frame
  interval, the loop renders the newest state next. Lag never accumulates.

## Lifecycle and failure handling (`daemon.py`)

- **State file** `~/.config/logitech-lighting/wave.json`, holding
  `{"preset": "red"|"blue", "paused": bool}`.
  - Written on every change and read at start.
  - Default: `red`, not paused.
  - A corrupt file is logged and replaced with the default.
- **Control socket** `$XDG_RUNTIME_DIR/g815-wave.sock`, a Unix stream
  socket with mode 0600. Each request and reply is one JSON line:
  - `{"cmd":"preset","name":"red"}`, `{"cmd":"off"}`, `{"cmd":"status"}`.
  - Replies are `{"ok":true,...}` or `{"ok":false,"error":"..."}`.
  - Unknown commands or presets return `ok:false` with the valid choices.
- **Single instance.** If the socket path is in use and answers, the new
  daemon exits with an error. A stale socket file that does not answer is
  removed.
- **CLI when the daemon is not running:** `wave` actions print
  `wave daemon not running — start it with: systemctl --user start g815-wave`
  and exit 1.
- **Keyboard unplugged or gone:** release state is dropped, the daemon
  enters *waiting*, and it polls enumeration every 2 s. When the keyboard
  reappears: claim, then full base paint.
- **Onboard takeover** (suspend/resume, an unnoticed replug, another
  program): every 10 s the daemon reads the onboard mode (`0x8100` fn 2).
  If it is not host mode, it re-claims.
- **Lock screen.** Once per second the daemon polls
  `gdbus call --session --dest org.gnome.ScreenSaver --object-path
  /org/gnome/ScreenSaver --method org.gnome.ScreenSaver.GetActive`
  (`/usr/bin/gdbus`, already present). The reply is `(true,)` or `(false,)`.
  - Rings pause while the screen is locked and resume on unlock (unless
    `wave off` is in effect). Polling avoids adding D-Bus Python bindings to
    the venv; the cost is a pause latency of up to ~1 s.
  - If `gdbus` is missing, the call fails, or the reply cannot be parsed, the
    daemon logs one warning and runs without the pause.
- **X session loss** (connection error): release the keyboard and exit
  non-zero. The service restarts with the next session.
- **Logging** goes to stdout/stderr, which systemd sends to the journal.
  No keystroke content is ever logged; only counts and fps.

## Privacy and security

- The daemon keeps key events only in memory, as ring origins that live
  ~1.2 s. It writes no keystrokes to disk or network.
- On X11, any client in the session can already observe key events, so the
  daemon adds no new capability. Using X11 avoids joining the `input`
  group.
- The visible ripple reveals which key was pressed (shoulder-surfing or
  cameras). The user accepted this; the only mitigations are the
  lock-screen pause and `wave off`.
- The udev rule from Phase 1 already restricts group access to interface 1
  (the HID++ node). The daemon needs nothing more.

## Testing

**Unit tests (pytest).** New files go in `g560ctl/test/test_new_g815_*.py`,
the convention for the live package. No hardware or X server is needed.
- `layout`: every key has a unique zone and a unique position. Zones match
  the Phase 1 map. X11 keycode mapping covers the main block.
- `presets`: gradient endpoints and midpoints, and quantization to 16 steps.
- `ripple`:
  - radius vs time;
  - band color at a known distance;
  - expiry at 1.2 s;
  - the origin flash;
  - the 8-ring cap dropping the oldest;
  - max-intensity overlap;
  - pause ignores presses;
  - idle frame is all base.
- `frame`:
  - no change gives no packets;
  - runs → fn 5, shared colors → fn 6, singletons → fn 1, each with the
    exact bytes;
  - invalid zones are never emitted;
  - resync rotation.
- `hidpp`, against a fake device (the pattern of Phase 1's check4):
  - sw_id rotation and matching;
  - a stale reply is ignored;
  - BUSY on frameEnd is retried;
  - the window shrinks on a lost reply;
  - claim/release byte sequences;
  - zone-bitmap parsing.
- `daemon`/CLI, in process:
  - socket preset/off/status;
  - the state file round-trip and corrupt-file fallback;
  - the "daemon not running" error;
  - the single-instance check.
- The existing 27 tests must still pass.

**Hardware checks, by eye:**
1. Claim-verification probe (the first task).
2. Ripple with both presets, typing slow and fast.
3. `wave off` returns to onboard lighting; `wave red` resumes.
4. Locking the screen pauses the rings.
5. Unplug/replug while running.
6. Suspend/resume.
7. Logout/login.
8. `wave status` shows a measured fps of at least 30.
9. `./lights solid ...` still drives the G560.

## Out of scope

- Wayland and console input. If ever needed, an evdev source would replace
  `keys.py`.
- More presets or effects, a GUI/TUI for wave, and per-app pausing.
- Changing the G560 code path, `DeviceConfig`, or `UnifiedController`.
- Deleting `experiments/`. The spike stays as the reference.
