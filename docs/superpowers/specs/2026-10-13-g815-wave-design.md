# G815 wave (ripple-on-keypress) — design

**Date:** 2026-10-13
**Status:** Approved in conversation (pending written-spec review)
**Supersedes:** Phases 2 and 3 of
`docs/superpowers/specs/2026-07-14-g815-static-controller-experiment-design.md`,
merged into one project.
**Builds on:** the Phase 1 spike, `experiments/g815_probe.py` and its findings
log `experiments/README.md`.

## Goal

When a key is pressed on the Logitech G815 (`046d:c33f`), a ring of light
expands from that key across the keyboard over a dark base color. The effect
runs as a background service from login. You switch it with the existing
`ligths` / `./lights` command. It uses our own Python code: OpenRGB, Solaar and
g810-led are references only, never runtime dependencies.

## Decisions (from the design conversation)

| Topic | Decision |
| --- | --- |
| Look | Expanding ring from the pressed key (classic ripple) |
| Ring colors | A gradient across the ring band, leading edge → tail; more than two colors |
| Base | Dark blue/purple, `#1e003c` (brightened from `#140028` on 2026-10-14) |
| Presets | `red`: `#ffffff` → `#ff2a2a` → `#b0005a` → base. `blue`: `#ffffff` → `#33ccff` → `#1f4fff` → base |
| Running | systemd **user** service, started with the graphical session |
| Switching | `ligths wave red|blue|off|status` (via `./lights`), no restart needed |
| Keypress source | **X11** (python-xlib, filtered to the G815 device). No `input` group membership |
| Code location | Inside the live `logitech_lighting` package; the G560 path is untouched |
| Lock screen | Rings keep running on the lock screen. *Changed 2026-10-14:* the original pause was dropped; the user accepts that the ripples show which keys were pressed |
| Privacy mode | Not wanted. The visible key-position exposure is accepted |

Rejected alternatives: evdev input (needs the `input` group, which lets any
user process read all typing); a standalone script under `experiments/`
(doesn't fit the `ligths` integration).

## Architecture

New subpackage `g560ctl/src/logitech_lighting/devices/g815/`. It sits alongside
the G560 and does not implement `DeviceConfig` / `UnifiedController`, which
model 4 zones with effects run on the device over USB control transfers.

| Module | Responsibility | Pure? |
| --- | --- | --- |
| `layout.py` | Key table: name → zone id → physical center `(x, y)` in key units (1 unit = one letter-key width), US ANSI full-size + G1-G5, media keys, logo. Also X11 keycode → key name. | yes |
| `presets.py` | Base color, the two presets as gradient stops, gradient interpolation, color quantization | yes |
| `ripple.py` | Effect state: active rings, `press(key, t)`, `render(t) -> {zone: (r,g,b)}`, pause/resume | yes |
| `frame.py` | Encoder: previous frame + new frame + valid zone set → list of HID++ packets | yes |
| `hidpp.py` | HID++ 2.0 transport over hidraw: open, feature discovery, pipelined send with reply matching, BUSY handling, claim/release, zone discovery | no |
| `keys.py` | X11 XInput2 raw key-press listener for the G815 device(s) only (see [Keypress input](#keypress-input-keyspy)) | no |
| `state.py` | Daemon state machine: OFF / ACTIVE / DISCONNECTED transitions and what each requires of the keyboard | yes |
| `daemon.py` | Main loop, control socket, state file, lock-screen watch, reconnect | no |

Data flow per frame (target 60 fps):
`keys.py` press events → `ripple.render(t)` → `frame.encode(prev, next)` →
`hidpp.send_frame(packets)` (pipelined, then frameEnd).

### CLI and service

- `logitech_lighting/cli.py` gains a `wave` subcommand with these actions:
  - `wave red` / `wave blue`: select the preset and resume rings.
  - `wave off`: pause rings and hand the keyboard back to onboard lighting.
  - `wave status`: preset, paused/active, keyboard connected, measured fps.
  - `wave daemon`: run the daemon in the foreground (used by the service).
- `wave` needs no `--device` (it is G815-only), and the G560 commands are
  unchanged. `./lights` and `~/.local/bin/ligths` already pass arguments
  through, so `ligths wave red` works with no change to either wrapper.
- `cli.main` dispatches `wave` in an early branch, before
  `get_default_device()` / `UnifiedController(...)`. That way keyboard
  actions never initialize or probe the G560 path.
- The service unit is `~/.config/systemd/user/g815-wave.service`:
  - `ExecStart=<repo>/lights wave daemon`. `sg` supplies only the
    `logitech-lighting` group; X access comes from the environment below.
  - `After=`, `PartOf=` and `WantedBy=graphical-session.target`, so the unit
    stops with the session.
  - `Restart=on-failure`, `RestartSec=5`.
- X environment:
  - The daemon needs `DISPLAY` and `XAUTHORITY` from the systemd user
    manager. On this machine GNOME already imports them: `DISPLAY=:1`,
    `XAUTHORITY=/run/user/1000/gdm/Xauthority`, and
    `graphical-session.target` is active (checked 2026-10-13).
  - At startup the daemon validates both. If either is missing it exits
    with code 0 and logs the hint `systemctl --user import-environment
    DISPLAY XAUTHORITY`, so a clean exit does not burn restart attempts.
- X session loss is also a clean exit 0: the session target is going away,
  and the next login starts the unit again. Only unexpected errors exit
  non-zero and use `Restart=on-failure`.
- The repo keeps the unit file and the docs explain how to install it (a
  one-time `systemctl --user enable --now`).
- Dependency: add `hidapi` (pinned `>=0.14`, using `import hidraw`, never
  `hid`) and `python-xlib` (`>=0.29`) to `pyproject.toml`.

### Keypress input (`keys.py`)

`python-xlib` 0.29 negotiates XI **2.0** in its helper and registers no
decoder for `RawKeyPress` (verified on this machine). XI 2.0 can miss raw
events while another client holds a grab, and only XI 2.1+ reliably delivers
the source device id that we filter on. So `keys.py` does three things
itself:
- It sends `XIQueryVersion` requesting **2.2** with the `XInputExtension`
  opcode and requires the server to answer ≥ 2.1. If the server is older, the
  daemon exits with a clear error.
- It selects events on the root window with **two separate masks**:
  `XI_RawKeyPress` for `XIAllMasterDevices`, and `XI_HierarchyChanged` for
  `XIAllDevices`. The XI2 protocol rejects hierarchy events selected for
  `XIAllMasterDevices` with `BadValue`.
- It decodes the raw generic-event bytes itself (`deviceid`, `time`,
  `detail` = keycode, `sourceid`). This decoder is small and is unit-tested
  on recorded byte samples.

G815 filtering:
- The daemon resolves the G815's *slave keyboard* device ids by name through
  `XIQueryDevice`. Today these are "Logitech G815 RGB MECHANICAL GAMING
  KEYBOARD" and "… Keyboard", ids 15/16.
- It accepts only raw events whose `sourceid` is in that set.
- On `XI_HierarchyChanged` (replug, re-enumeration) it re-resolves the ids.

Keycode mapping:
- X keycode − 8 = evdev keycode. `layout.py` maps evdev keycode → key name
  → zone.
- Unmapped keycodes are ignored, with a per-keycode debug log once (the
  keycode number only; it is not stored).

**Feasibility gate (Gate B, before the daemon is built):**
- A probe prints the key *name* for G815 presses only.
- It shows that presses from another keyboard (the G502's keyboard
  interface) are ignored.
- It checks that events still arrive while a keyboard grab is held: the
  GNOME overview, or an open application menu.
- It checks that ids re-resolve after a replug.

## The effect (`ripple.py`, `presets.py`, `layout.py`)

- **Geometry.** Each key has a physical center in key units, and a ring's
  distance to a key is the Euclidean distance between their centers.
- **One ring.** Born at the pressed key's center at time `t0`.
  - The radius is `r(t) = 25 units/s × (t − t0)`.
  - The band is 3 units wide behind the leading edge.
  - For a key at distance `d`, the band position is `u = (r − d) / 3`. When
    `0 ≤ u ≤ 1` the key is on the band: `u = 0` is the leading edge, `u = 1`
    the tail.
  - Its color is `gradient(u)` from the preset stops.
  - Its intensity is the ring's age envelope, which falls linearly to 0 at
    1.2 s.
  - The final color is `lerp(base, gradient(u), intensity)`.
- **Origin flash.** The pressed key shows the first gradient stop at full
  intensity for its first 80 ms.
- **Many rings.**
  - At most 8 live rings; a ninth press drops the oldest.
  - Rings expire at 1.2 s.
  - Where rings overlap, a key takes the contribution with the highest
    intensity. They are not added together.
- **Quantization.** Both inputs of the final color are quantized: the band
  position `u` to 8 steps and the intensity to 16 steps. Every frame color
  therefore comes from a fixed palette of at most 8 × 16 + 1 = 129 colors per
  preset (the +1 is the base). In practice a frame holds far fewer, because
  keys at similar distances share a step. That lets the encoder group keys.
- **Pause and clear.** `ripple` exposes two operations:
  - `pause()`: `press()` is ignored, and existing rings finish naturally. Used
    for the transition into OFF, where it is moot because control is
    released.
  - `clear()`: drops all rings at once, so the next frame is all base. Used
    when the screen locks. It never lets an in-flight ring keep revealing
    keys.
- **Idle.** With no live rings, `render` returns the all-base frame. The
  encoder then emits nothing, because nothing changed.

All numeric values (speed, band width, lifetime, flash, max rings,
quantization steps, colors) are named constants in `presets.py` /
`ripple.py`, so they can be tuned after we see the effect on the keyboard.

## Talking to the keyboard (`hidpp.py`, `frame.py`)

Phase 1 facts carried forward:
- **Interface.** hidapi `hidraw` entry with usage page `0xFF43`, usage
  `0x0602` (interface 1). The kernel input driver stays attached.
- **Report format.** HID++ long reports only: `0x11`, device `0xFF`,
  20 bytes.
- **Feature indexes.** Discovered at runtime via the root feature
  getFeature, never hardcoded. Seen so far: `0x8081` per-key lighting v2,
  `0x8071` RGB effects, `0x8100` onboard profiles.
- **Zone ids.** Main block = HID usage − 3 (`0x01-0x67`), modifiers
  `0x68-0x6f`, `0x99` (backlight/indicator key), media `0x9b-0x9e`, G1-G5
  `0xb4-0xb8`, logo `0xd2`.

**Claim (take software control), candidate sequence.** The real order is
an *outcome* of Gate A below. Solaar and OpenRGB differ here, and OpenRGB
adds a G815-family `0x4522` handshake.
1. Discover the feature indexes.
2. `0x8071` SetSWControl. This stops the onboard effect engine; without
   it, the keyboard reverts to onboard colors after a few seconds
   (Solaar PR #3165).
3. `0x8100` setOnboardMode = `0x02` (host).
4. Zone discovery: `0x8081` fn 0, pages 0-2, giving a bitmap of valid
   zones. Compare it against `layout.py`. A layout zone the device does
   not report is dropped and logged once, never sent.
5. Paint the full base frame and send frameEnd. Every write and the
   frameEnd must be acknowledged. Only then is the claim complete.

**Optional features.**
- If `0x8071` is absent, step 2 is skipped. Absence is legal, and we
  rely on host mode.
- If `0x8100` is absent, step 3 is skipped.
- If `0x8081` is absent, the claim fails: the daemon logs it and stays
  DISCONNECTED.

**Partial-claim rollback.** If any step fails, the steps already applied
are undone in reverse order (SetSWControl off, onboard mode back to `0x01`),
best effort. The claim then counts as failed and is retried with backoff
(2 s, 4 s, … capped at 30 s).

**Release:** undoes only the steps the claim actually applied: SetSWControl
off if `0x8071` was used, then setOnboardMode = `0x01` if `0x8100` was used,
then **re-select the current profile**: getCurrentProfile (`0x8100` fn 4,
reply params bytes 0-1) and setCurrentProfile (`0x8100` fn 3) with those two
bytes. Gate A showed onboard mode alone leaves the last host frame on the
keys until a profile is (re)selected, e.g. by pressing M1/M2. The claim records which features exist; release, rollback and monitoring
all read that record.

**Gate A, claim and throughput (the first implementation task, on
hardware, before `frame.py`/`hidpp.py` are built on top).** A probe script
settles and records these points:
- The exact SetSWControl parameter bytes for the G815.
- Whether the `0x4522` (DisableKeysByUsage) handshake is needed. It is
  needed if colors revert or keys misbehave without it.
- Whether host mode breaks G-key lighting (OpenRGB has this quirk on the
  G915 TKL).
- That the base frame is visible after the claim and *stays* visible for
  60 s without repainting.
- That fn 1 (individual) and fn 5 (range) work on the G815, with exact
  byte layouts confirmed.
- That fn 0 zone discovery returns the Phase 1 zone set.
- Which per-key writes echo their payload in the reply, and that the
  root-feature ping echoes its ping byte. Reply ordering is recorded for
  information only; safety does not depend on it (see Sending).
- **Sustained committed fps** with synthetic input: a scripted burst of fast
  presses (≥ 10 presses/s) with 8 overlapping rings, rendered and encoded by
  the real effect code, sent with the pipelined sender. **Pass: ≥ 30
  committed frames/s.** If it fails, before building further: drop the
  target to what is measured, coarsen quantization (fewer `u` steps), or
  narrow the ring band. Then record the chosen values.

The verified sequence and numbers are written into this spec (a dated
"Gate A results" section) before `frame.py` and `hidpp.py` are built.

**Frame encoding (`frame.py`, pure).** Input: previous frame, next frame and
the valid zone set. Output: packets.
- Only zones whose color changed (plus resync zones) are sent. The
  previous-frame cache holds what the keyboard is **confirmed** to show
  (see "Commit rule").
- Packets are grouped to minimise the count:
  - fn 5 setRangeRgbZones for runs of ≥3 consecutive zones with one color;
  - fn 6 setRgbZonesSingleValue (≤13 zones) for scattered zones sharing a
    color. A short packet is padded by repeating one of its own (valid)
    zones, never with filler bytes (as in Phase 1);
  - fn 1 setIndividualRgbZones (4 zones/packet) for colors used once.
- Each frame **that already changes something** also re-sends 2-3 zones in
  rotation, so a write that was acknowledged but dropped heals quickly while
  rings run. Idle frames send nothing at all (no resync); the 10 s full
  repaint covers drift while idle. *(Ruling 2026-10-14, final review: the
  earlier text resent zones on every frame, contradicting "idle frames emit
  no packets" and costing ~120 HID++ reports/s around the clock.)*
- A frame with no changes and no resync zones yields no packets and no
  frameEnd.
- Exact fn 1/fn 5 byte layouts are taken from Solaar `PerKeyLighting` and
  OpenRGB `LogitechHIDPP20Controller`, and pinned by unit tests.

**Sending (`hidpp.py`).** There are two paths, with separate rules.

*Request tracking (both paths).*
- Each outstanding request gets an sw_id from 1-15 and an in-flight entry
  holding (feature index, function, sw_id, parameter bytes, deadline).
- A report is matched **by type**:
  - *Success reply* `11 ff <feat> <fn|sw> …`: matches the open entry with the
    same (feature index, function, sw_id).
  - *Payload check.* Gate A showed per-key writes echo only a prefix of
    their parameters: fn 1 and fn 5 echo byte 0, fn 6 echoes bytes 0-3
    (rgb + first zone); the rest of the reply is zero. The reply's echoed
    prefix must equal the request's. Requests whose reply carries data (root getFeature, zone
    discovery, getOnboardMode) are matched on the header only.
  - *Ping reply* (root getProtocolVersion): matched on the header **and**
    the echoed ping byte at response parameter 2 (IRoot spec).
  - *Error reply* `11 ff ff <feat> <fn|sw> <code>`: matches on bytes 3-4
    against the entry's (feature index, function|sw_id).
  - *Anything else* (input reports, notifications, replies matching no open
    entry) is counted and dropped.
- An sw_id is **reusable only after its entry is closed by a matching
  reply**. A timed-out id is **quarantined** for the life of the device
  connection: re-claims and handle reopens do **not** lift it, whatever the
  fence below shows. Safety therefore does not depend on reply ordering or
  on how late a reply arrives.
- With at most 4 entries in flight and 15 ids, ids never wrap around onto a
  live entry. If quarantine leaves fewer free ids than the window plus one
  (for the fence), the window shrinks to fit, overriding the window's
  minimum of 2 below; below 3 free ids (window 2 + fence) the sender stops
  sending and the daemon goes DISCONNECTED.
- A request counts as **timed out** (and its id is quarantined) only when no
  reply of any kind (success, BUSY or other error) arrives within 50 ms for
  frame-path requests including frameEnd, or 500 ms for control requests. A
  BUSY error reply closes the entry and frees its id. Gate A measured 0
  timeouts in 1,342 frames (40 s): all 11 frameEnd retries were BUSY
  (`0x08`), so quarantine is not expected to exhaust ids in practice.
- **Fence after any timeout.** Before the next frame or control request,
  the sender sends a root-feature **ping** (getProtocolVersion, fn 1) with a
  fresh sw_id and a ping byte unique to this fence. The device echoes the
  ping byte back.
  - Reports arriving before the matching ping reply (header + echoed byte)
    are discarded.
  - The fence only clears the read buffer of replies that are already
    late. It frees no ids, because those stay quarantined.
  - If the ping itself times out (500 ms), the connection is treated as
    gone → DISCONNECTED.
- **Only re-enumeration lifts quarantine.** A re-claim closes the hidraw
  handle, waits 1 s, and reopens it, but the quarantine set carries over to
  the new handle: a stale reply (even a getFeature reply) that lands in the
  new handle's buffer can only carry a quarantined id, so it matches nothing
  and fresh discovery cannot pick up a wrong feature index. The quarantine
  resets only when the device re-enumerates (its hidraw node disappears and
  a new one appears, e.g. a replug), because a re-enumerated device has
  reset its HID++ state.

*Frame path (per-key writes + frameEnd).*
- **Write pacing (Gate A).** The G815 silently drops writes sent
  back-to-back: of 6 writes sent with no gap only the last was
  acknowledged; with ≥ 1 ms between writes all were. Consecutive writes are
  therefore spaced at least **1 ms** apart, measured on the monotonic clock
  from the previous write's return. A 0.5 ms gap still dropped writes, so
  the margin is thin and the constant must not be lowered.
- **Pipelining window.** At most N writes are unacknowledged, starting at
  N = 4. N halves (min 2) after any lost reply and grows by 1 after 16
  clean frames, back up to 4. Gate A measured window 2 and window 4 alike
  (≈ 33-34 fps); a larger window gained nothing.
- **Commit rule.** frameEnd is sent only after **every** write of that frame
  is acknowledged OK. If any write fails, is BUSY, or misses the frame
  deadline (60 ms from the frame's first write), the frame is abandoned:
  - frameEnd is not sent;
  - the connection is drained;
  - the confirmed-frame cache is marked **uncertain**, and the next frame is
    a **full repaint** of every valid zone.
- **BUSY on frameEnd** is backpressure, not failure.
  - Sleep a learned time per zone written (smoothed, capped at 100 ms),
    then retry frameEnd every 3 ms until it is acknowledged or 150 ms pass.
  - Only an **acknowledged** frameEnd advances the confirmed-frame cache to
    this frame. A frameEnd that is never acknowledged leaves the cache
    uncertain, and the next frame is a full repaint.
- Frame writes are never retried individually. The full-repaint rule heals
  them instead, so the 60 ms frame deadline has no competing retry timers.
- **Frame skipping.** If rendering plus sending overruns the frame
  interval, the loop renders the newest state next. Lag never accumulates.

*Control path (claim, release, mode read, zone discovery).*
- Sent one at a time (window 1).
- BUSY → retry after 30 / 60 / 90 ms, then fail.
- This path never runs while a frame is in flight.

*Escalation.*
- 3 abandoned frames in a row → release + re-claim.
- A write/read OSError (or `write()` returning −1) means the keyboard is
  gone → DISCONNECTED.

## Lifecycle and failure handling (`daemon.py`)

**States (`state.py`, pure).** The user's choice and the observed
conditions combine into exactly one state:

| State | When | Keyboard | Rings |
| --- | --- | --- | --- |
| **OFF** | user chose `wave off` | **released** (onboard effect) | none |
| **DISCONNECTED** | user wants wave, keyboard absent or claim failed | n/a, polling every 2 s | none |
| **ACTIVE** | user wants wave, connected (locked screen or not) | claimed | live |

Rules:
- **OFF is sticky.** In OFF, a keyboard reconnect, resume or onboard
  takeover never triggers a claim. Only `wave red|blue` leaves OFF.
- **DISCONNECTED → (claim OK) → ACTIVE.** Leaving ACTIVE clears all rings.

- **State file** `~/.config/logitech-lighting/wave.json`, holding
  `{"preset": "red"|"blue", "off": bool}` (the user's choice only; observed
  conditions are never persisted).
  - Written on every change and read at start.
  - Default: `blue`, not off (changed from `red` on 2026-10-14 at the user's request).
  - A corrupt file is logged and replaced with the default.
- **Control socket** `$XDG_RUNTIME_DIR/g815-wave.sock`, a Unix stream
  socket with mode 0600. Each request and reply is one JSON line:
  - `{"cmd":"preset","name":"red"}`, `{"cmd":"off"}`, `{"cmd":"status"}`.
  - Replies are `{"ok":true,...}` or `{"ok":false,"error":"..."}`.
  - Unknown commands or presets return `ok:false` with the valid choices.
- **Single instance.** The authority is an exclusive `flock` on
  `$XDG_RUNTIME_DIR/g815-wave.lock`, held for the daemon's lifetime.
  - A daemon that cannot take the lock exits with "already running", even
    if the socket probe times out because the running daemon is slow.
  - Only the lock holder may unlink and re-create the socket path. A stale
    socket file is therefore removed only once staleness is proven by
    holding the lock.
  - Simultaneous startup is safe: exactly one wins the lock.
- **CLI when the daemon is not running:** `wave` actions print
  `wave daemon not running — start it with: systemctl --user start g815-wave`
  and exit 1.
- **Keyboard unplugged or gone** → DISCONNECTED: the hidraw handle is
  closed and the device is polled every 2 s. When it reappears and the user
  is not OFF: claim (with full repaint), then ACTIVE.
- **Onboard takeover** (suspend/resume, an unnoticed replug, another
  program): every 10 s, outside OFF, the daemon checks control on the
  control path. If `0x8100` exists, it reads the onboard mode (fn 2); a
  mode that is not host means takeover. Without `0x8100` there is no
  mode read, so the daemon **re-asserts** instead every 10 s: it re-sends
  SetSWControl (if `0x8071` exists) and does a full repaint of the current
  frame. Idle frames emit no packets, so this re-assert is what heals drift
  while nothing is happening. On a detected takeover, or a re-assert that
  fails, the cache is marked uncertain and the daemon re-claims.
- **Periodic repaint in every case.** Even with `0x8100`, every 10 s while
  idle the current frame is fully repainted once. This catches keys that
  drifted without a mode change.
- **Lock screen.** Not watched: rings run on the lock screen too (user
  decision, 2026-10-14). History, for anyone re-adding a pause: GNOME's
  `org.gnome.ScreenSaver.GetActive` was unreliable on this Pop!_OS 22.04
  session (locked for only 8 s of one lock, never during the next), while
  logind's `LockedHint` (`loginctl show-user <uid> -p Display --value`, then
  `loginctl show-session <id> -p LockedHint --value`) flipped exactly at lock
  and unlock.
- **X session loss** (connection error): release the keyboard and exit 0.
  The unit is `PartOf=graphical-session.target` and starts again with the
  next session (see CLI and service).
- **Shutdown** (SIGTERM/SIGINT): release the keyboard (unless OFF, where it
  is already released), remove the socket, drop the lock, exit 0.
- **Logging** goes to stdout/stderr, which systemd sends to the journal.
  No keystroke content is ever logged; only counts and fps.

## Privacy and security

- The daemon keeps key events only in memory, as ring origins that live
  ~1.2 s. It writes no keystrokes to disk or network.
- On X11, any client in the session can already observe key events, so the
  daemon adds no new capability. Using X11 avoids joining the `input`
  group.
- The visible ripple reveals which key was pressed (shoulder-surfing or
  cameras). The user accepted this, including on the lock screen; the only
  mitigation is `wave off`.
- The udev rule from Phase 1 already restricts group access to interface 1
  (the HID++ node). The daemon needs nothing more. Caveat: interface 1 also
  declares an NKRO keyboard collection. In NKRO mode, typing could appear
  on that node, readable by `logitech-lighting` group members. The daemon
  does not use it: input comes from X11, and the HID++ reader discards
  non-`0x11` reports without logging them.

## Build order and gates

Single coherent feature, one plan. The order is fixed by risk:
1. **Gate A**: claim sequence + committed-fps probe on hardware (see
   [Talking to the keyboard](#talking-to-the-keyboard-hidpppy-framepy)).
   This needs `layout`/`presets`/`ripple` first, so those pure modules come
   before the gate.
2. **Gate B**: XI2 raw-input probe (see [Keypress input](#keypress-input-keyspy)).
3. Only after both gates pass: `frame.py` / `hidpp.py` in final form,
   `state.py`, `daemon.py`, CLI, and the service unit.

If a gate fails, stop and revise this spec. Do not build past it.

## Testing

**Unit tests (pytest).** New files go in `g560ctl/test/test_new_g815_*.py`,
the convention for the live package. No hardware or X server is needed.
- `layout`:
  - every key has a unique zone and a unique position;
  - zones match the Phase 1 map;
  - the evdev keycode mapping covers the main block.
- `presets`: gradient endpoints and midpoints; quantization of `u` (8 steps)
  and intensity (16 steps); a palette of at most 129 colors.
- `ripple`:
  - radius vs time;
  - band color at a known distance;
  - expiry at 1.2 s;
  - the origin flash;
  - the 8-ring cap dropping the oldest;
  - max-intensity overlap;
  - `pause()` ignores presses;
  - `clear()` gives an all-base frame immediately;
  - an idle frame is all base.
- `frame`:
  - no change gives no packets;
  - runs → fn 5, shared colors → fn 6 (padding repeats a valid zone),
    singletons → fn 1, each with exact bytes;
  - invalid zones are never emitted;
  - resync rotation;
  - an uncertain cache gives a full repaint.
- `hidpp`, against a scripted fake device (the Phase 1 check4 pattern), with
  fault injection:
  - sw_id allocation never reuses an open id across wraparound;
  - a reply with the right sw_id but the wrong echoed payload is ignored;
  - out-of-order replies within the window;
  - a late reply after a timeout is discarded by the fence, never matched;
  - a reply arriving *after* the fence completes, for a quarantined id, is
    dropped (and the id stays quarantined when ordering is not trusted);
  - getFeature/zone-discovery replies match on the header despite a data
    payload, and error replies match on bytes 3-4;
  - a ping timeout → disconnected;
  - a ping reply with the right header but the wrong ping byte does not
    complete the fence;
  - timed-out ids are never reused, including after a re-claim and handle
    reopen; they are freed only by re-enumeration;
  - a stale getFeature reply for a quarantined id, arriving on the new
    handle after a reopen, does not match fresh discovery;
  - too few free ids shrink the window, and fewer than 3 stop sending
    (DISCONNECTED);
  - a BUSY reply frees its id; only a missing reply quarantines it;
  - consecutive writes are never less than 1 ms apart;
  - without `0x8100`, the 10 s re-assert sends SetSWControl plus a full
    repaint; with it, the idle 10 s repaint still happens;
  - the window halves on a lost reply and grows after clean frames, up to 4;
  - **partial frame failure** (one write BUSY/error) → no frameEnd, cache
    uncertain, next frame is a full repaint;
  - BUSY on frameEnd is retried until acknowledged;
  - a frameEnd never acknowledged → cache uncertain;
  - control-path BUSY retries at 30/60/90 ms;
  - OSError and a `write()` of −1 → disconnected;
  - claim/release byte sequences and partial-claim rollback;
  - optional features absent: release and monitoring skip `0x8071`/`0x8100`
    when the claim did not use them;
  - zone-bitmap parsing.
- `keys`: the raw-event decoder on recorded `XI_RawKeyPress` byte samples;
  the sourceid filter; device-id re-resolution after a hierarchy change

- `state`: every transition in the States table. OFF stays released across

## G-key ripples (addition, 2026-10-13)

Requested after Part 2's smoke run. In host mode the G-keys send nothing to X
(verified: no X key events for G1-G5 while the wave was active).
- `0x8010` GKey is at index `0x0a` and `0x8020` MKeys at `0x0b` on this G815.
- `0x8010` fn 2 `[01]` diverts the keys (Solaar's "Divert G and M Keys"). Each
  change then arrives as a notification `11 ff 0a 00 <mask>`: G1-G5 are bits
  0-4, and `00` means released. M1-M3 arrive as `11 ff 0b 00 <mask>`.
- The claim diverts the G-keys after host mode; the release undoes it first
  (`[00]`). Notifications use sw_id 0, which requests never use. The transport
  hands them to the keyboard, and the daemon reads them every tick, even when idle.
- A press is a newly set bit, and it starts a ring from that G-key's position.
  The M keys have no per-key LED zone and get no ring. They stay inert while
  the wave is on.
- Verified on hardware: the user saw rings from G1-G5.
